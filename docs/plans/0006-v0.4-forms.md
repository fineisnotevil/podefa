## 1. Goal and scope

The roadmap's v0.4: **fill AcroForms, flatten, export.**

| Feature | What "done" means |
| :--- | :--- |
| Fill | Text (one line, several lines, comb, password), check box, radio group, combo box (with or without typing), list (one or several choices); the value shows at once and is saved in the file; each change is one undo step |
| Navigate | Tab and Shift+Tab move between fields in order; Enter or Space toggles a check box; Esc leaves the field |
| Field state | Read-only fields cannot be changed; required fields are marked; hover shows the field's tooltip (`/TU`) |
| Reset | The whole form, or one field, back to its default value (one undo step) |
| Flatten | The fields become page content, as they look; one undo step |
| Export, import | The form's values to a file and back (formats: §9 question 3) |
| JavaScript | Calculated fields, formatting and validation, only if §9 question 2 says so |

**Out of scope, not designed out:** creating or editing fields (a form designer), XFA forms (MuPDF
does not read them; an XFA-only document shows its fallback page), digital signatures (v0.5;
signature fields are shown and left alone), submit actions (sending a form to a server).

## 2. What exists and what has to change

- **Widgets are drawn already.** Tiles come from display lists made with annotations
  (`DRAW_ANNOTATIONS`, `crates/engine-mupdf/src/lib.rs`), so a form's fields show as their
  appearance streams say. They cannot be changed.
- **The annotation layer leaves widgets out** on purpose (`edit.rs`: `T::Widget` returns `None`;
  `copy_annotations` skips them). v0.4 adds a field layer beside it, not inside it.
- **Every edit is one journal operation** (`EngineCmd::Edit`, ADR 0008) that changes one page:
  `Change::Page` bumps that page's revision, and its tiles are redrawn. A field value is the same
  kind of change - except that one field can have widgets on several pages (a radio group, or the
  same field shown twice), so a fill may change more than one page.
- **The Note editor** (Plan 0004 Phase 3) is the pattern for editing in place: a Slint editor laid
  over the page at the item's rectangle, committed as one edit.

## 3. Phase 0 findings (verified, with evidence)

Measured with `crates/engine-mupdf/tests/forms_bench.rs` (ignored; release build, 2026-10-23, the
§1 machine of `benchmarks.md`) on a generated form with every field type. The numbers are in
`benchmarks.md` §12.1.

### 3.1 mupdf-rs 0.8 reads and fills every field type

`PdfPage::widgets`, and on each `PdfWidget` (`patches/mupdf/src/pdf/widget.rs`):

- `r#type` (text, check box, radio, combo, list, signature, push button), `name`, `value`,
  `label`, `field_flags` (read-only, required, multi-line, comb, password, combo, edit,
  multi-select, radio, no-toggle-to-off);
- `set_value(doc, value, ignore_trigger_events)` (`pdf_set_field_value`), `reset`, `update`;
- the widget's rectangle through its annotation.

On the generated form, every field took its value and kept it:

- a check box takes `Yes`, a radio group its button's state (`b`);
- a combo box takes `Muğla` from Turkish options in UTF-16;
- a multi-select list takes `en`;
- a multi-line field takes two lines with Turkish letters.

Each fill inside `begin_operation` / `end_operation` was one journal step: undo and redo moved
between the values. An incremental save kept them, and they read back after reopening. Reading the
11 widgets took 2.1 ms. A fill took 0.3-0.8 ms, except for the Turkish text in §3.2.

### 3.2 Found: Turkish text in a field cost 2.4-3.5 s per fill, and the fix

Measured costs:

| Fill | Time |
| :--- | ---: |
| ASCII text | 0.4 ms |
| "Öz" (letters Helvetica's WinAnsi encoding has) | 0.4 ms |
| "Öğüt Şükrü İnce" | 3540 ms |
| Multi-line Turkish text | 2484 ms |
| "Muğla" in the combo box | 2676 ms |

This happens with the engine's font loader installed. Flattening the filled form took 917 ms.

- **Why:** letters outside the field font's encoding (ğ, ş, İ, ı) make MuPDF's appearance code
  ask the font loaders for a generic font named `serif`, three times per fill. The engine's loader
  (`fonts.rs`, `Base14First`) knows only the 14 standard names, so each request falls through to
  mupdf-rs' system font search (`font-kit`, a new `SystemSource` per request, plan 0005 §3.8).
  The appearance then embeds MuPDF's Nimbus Sans.
- **Checked:** a loader that maps `serif`, `sans-serif` and `monospace` to MuPDF's built-in Times,
  Helvetica and Courier brings the same fills to 2.1, 1.4 and 1.3 ms, and the flattening to
  1.3 ms. The prototype was removed again; Phase 1 makes it the engine's.
- **Wider effect:** any appearance MuPDF synthesizes with non-WinAnsi text pays the same cost today
  (v0.3 stamps write their own content with an embedded font, so they do not).

### 3.3 JavaScript: compiled in, did not calculate on the first try

- mupdf-rs' default features compile MuPDF's JavaScript (`js`, mujs; `docs/backlog.md` item 11).
  `PdfDocument::enable_js` and `calculate_form` exist.
- On the generated form, a total field with a calculation script did not calculate. Both scripts
  tried failed the same way, with "TypeError: cannot convert null to object" on stderr and the
  total left empty:
  - `AFSimple_Calculate("SUM", ...)`;
  - a plain `event.value = Number(this.getField("a").value) + ...`.
- Not investigated further in Phase 0: the cause may be in the fixture, in how fields are looked
  up, or in MuPDF's event set-up. §9 question 2 decides whether to go further.
- **Security:** document JavaScript is code from the file. MuPDF's mujs has no file or network
  access, but its event handlers run on every fill.

### 3.4 Flattening is an undoable edit

- `PdfDocument::bake(false, true)` inside one operation turned the 11 widgets into page content:
  - the filled text stays and becomes extractable;
  - 0 widgets are left.
- One undo brought all 11 back. So "Flatten form" can be an edit of the open document like any
  other, with a Save As for a flattened copy.
- `bake` does not collect garbage, so the §3.4 trap of Plan 0005 does not apply.

### 3.5 What mupdf-rs 0.8 lacks

| Need | MuPDF function | In mupdf-rs 0.8 |
| :--- | :--- | :--- |
| A choice field's options, to offer them | `pdf_choice_widget_options` (`pdf/form.h:94`) | no |
| Several values of a multi-select list | `pdf_choice_widget_value` / `_set_value` (`:105`, `:113`) | no (`set_value` sets one) |
| A check box's or radio button's "on" state name (`Yes`, `1`, `b`...) | `pdf_button_field_on_state` (`:176`) | no |
| A text field's maximum length | `pdf_text_widget_max_len` (`:77`) | no |
| The form-wide reset | `pdf_reset_form` (`:154`) | no (`reset` per widget exists) |

All of them throw, so they need `fz_try` wrappers like Plan 0005's (`journal/tools.c`, ADR 0008),
and an upstream pull request. The `/Opt` array and the appearance dictionary's state names can
also be read with the `PdfObject` API that already exists, without a shim.

### 3.6 Export formats

- MuPDF writes no FDF or XFDF. Both are small formats: FDF is a PDF-syntax dictionary of
  `/Fields`, and XFDF is its XML form, which Acrobat and most readers import.
- JSON or CSV of `name → value` is trivial. §9 question 3.

## 4. Design

### 4.1 Engine

- A field model in `core` (`pdf_core::form`): `FieldInfo { id, name, kind, value, options,
  on_state, flags, widgets: Vec<(page, rect)>, tooltip, max_len }`. `EngineCmd::Fields { page }`
  answers with the page's fields, as `Annotations` does for annotations.
- `EditOp::SetField { field, value }` and `EditOp::ResetForm { fields }`, each one journal
  operation. They report every page with a widget of the field: a new `Change::Pages`-like answer
  listing the changed pages, or one `Change::Page` per page.
- `EditOp::Flatten` (`bake`) changes every page with widgets.
- The font fix of §3.2 in `fonts.rs`.

### 4.2 App

- A click on a field with the Select tool:
  - focuses a text field: a Slint `LineEdit`, or `TextEdit` for several lines, laid over the
    widget's rectangle in the field's font size, as the Note editor is;
  - toggles a check box;
  - chooses a radio button;
  - opens a choice field's options as a popup list.
- Enter commits a line, Esc cancels, Tab commits and moves to the next field.
- Hovering a field shows its tooltip and a hand or text cursor. Required fields get an outline
  while the form is being filled.
- Forms menu: Reset Form, Flatten Form, Export Data..., Import Data...; Highlight Fields (a view
  setting).

### Phase 1 results (at the gate)

Implemented in:

- `f889703`: the font fix of §3.2.
- `fb8d5da`: core (`pdf_core::form`, `EditOp::SetField`).
- `e62d65b` and `0f0f5da`: engine (`engine-mupdf/src/form.rs`).
- `92478dc`: the app (`fields_ui.rs`) and `--bench-forms`.

fmt, clippy `-D warnings`, `cargo test --workspace` and `reuse lint` are clean on Windows.

**Engine:**

- `EngineCmd::Fields` lists a page's widgets: name, kind, value, rectangle, the button's "on"
  state, the choice's options (labels and export values, UTF-16 decoded), read-only, required,
  multi-line, password, editable, multi-select, maximum length, text size and tooltip. All of
  these come from the widget's dictionary through `PdfObject`, with no shim (§3.5).
- `EditOp::SetField` is one journal operation, with trigger events ignored (no JavaScript, §0):
  - a field with widgets on one page answers as a page edit;
  - one with widgets on several pages changes them all, reported like a stamp (ADR 0009 map,
    the changed pages to none);
  - every widget of the field gets its new appearance inside the operation, so undo takes it
    back too.
- `Opened` carries a `FormSummary` (fields, scripts, XFA). The status bar says when a form has
  scripts PODEFA does not run, or is XFA.
- **The font fix (§3.2):** `serif`, `sans-serif` and `monospace` are MuPDF's built-in Times,
  Helvetica and Courier.

**App:** with the Select tool:

- A click on a check box toggles it; a click on a radio button turns it on.
- A click on a text field opens an editor laid over it: its rectangle, its text size scaled to
  the zoom, password fields masked. It keeps up with scrolling and zooming.
  - Enter commits (Ctrl+Enter in a multi-line field), and so do Tab and a click elsewhere.
  - Esc cancels. The field's maximum length is applied.
- A click on a combo or list box opens its options under it (above when the view ends); an
  editable combo box also gets the editor.
- The cursor over a field is a text cursor or a hand, and a field's tooltip shows on hover.
  Read-only and signature fields are left alone.

**Found and fixed on the way:**

- **Radio groups did not show their value.** mupdf-rs' `PdfWidget::set_value` hands MuPDF the
  widget, not the field. MuPDF sets the appearance states from the object it is given down
  through `/Kids` (`pdf-form.c`, `update_checkbox_selector`), so only the clicked widget was
  updated. The value was stored, but no button looked on. The engine now sets every widget's
  `/AS` of a button field.
- **Single-line Turkish text sat below its field.** For letters outside WinAnsi, Greek and KOI8-U,
  MuPDF lays field text out as rich text. For a single line, it computes the box as if y grew
  upwards in a stream where it grows downwards (`write_rich_content`), so the text was clipped to
  its upper part. MuPDF fixed it after 1.27.2 (Bug 709471, `184efba7dd` in 1.28.5); mupdf-rs
  builds an earlier MuPDF. The engine adds the missing translation to such appearances, only for
  single-line fields and only when the wrappers' headers are 1.27.2's. It goes with the next
  mupdf-rs release (`docs/backlog.md` items 10 and 17).

### Phase 2 results (at the gate)

**Engine and core:**

- **Tab order.** Each widget carries its place in its page's tab order (`FieldInfo::tab`), from
  the page's `/Tabs`:
  - `/R`: rows, top to bottom, each read left to right;
  - `/C`: columns, left to right, each read top to bottom;
  - otherwise (no `/Tabs`, or `/S`, structure order, which needs a tagged document's structure):
    the annotation order.

  Widgets whose rectangles overlap by half their height are on one row
  (`pdf_core::form::tab_places`), so fields drawn a fraction of a point apart, as on the
  maintainer's form, stay in reading order. `tab_sequence` leaves out what cannot be filled
  (read-only, signatures, push buttons).
- **Tab across pages.** `EngineCmd::NextFieldPage` answers with the next page that has a field
  that can be filled, before it for Shift+Tab, going round the document's end.
- **Multi-select lists.** `EditOp::SetChoices` sets several values as one step:
  - `/V` becomes an array of the chosen options' export strings, copied from `/Opt` so they keep
    the file's encoding (mupdf-rs' `new_string` cannot write UTF-16);
  - `/I` holds their indices;
  - a value that is not an option is refused.

  `FieldInfo::values` reports a choice field's chosen values.
- **Found: MuPDF 1.27.2 draws a list box without its value.** `pdf_write_ch_widget_appearance`
  writes every option, one per line ("TODO: Highlight selected items"). This is true of
  single-choice lists filled in Phase 1 too. The engine now draws a band, in the colour readers use
  for a list's selection, under each chosen row: one line is 1.116 times the text size, starting at
  `/TI`. An appearance of another shape is left as it is: a list laid out as rich text (options
  with letters outside WinAnsi, `docs/backlog.md` item 18) or another producer's.
- **Reset.** `EditOp::ResetField` and `EditOp::ResetForm` put fields back to `/DV`, or empty, off
  or none without one. Read-only fields are left alone. A reset of the whole form is one step,
  reported like a fill on several pages. A form that already has its defaults is refused with no
  step (`NothingToReset`).

**App:**

- Tab and Shift+Tab go from field to field: from the page in view when no field has the focus,
  over pages, round the end.
  - A text field opens its editor.
  - A combo box or list opens its options: Up, Down, Space and Enter work in them.
  - A check box or radio button is outlined; Space or Enter sets it.
  - Esc leaves the field. A click elsewhere leaves it too.
- From one text field to the next, the editor stays and takes the keys again
  (`field-editor-serial`).
- A multi-select list ticks and unticks its options (✓) until it closes. Enter, Tab or a click
  elsewhere keeps the ticks; Esc drops them.
- A new **Form** menu has Reset Field (the focused field) and Reset Form.
- **Read-only and required fields** (from Phase 1): read-only fields take no click or Tab; required
  fields have a red edge. Tooltips show on hover.

   flattened copy, or both?

   committed.
