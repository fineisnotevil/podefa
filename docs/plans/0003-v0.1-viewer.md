## 1. Goal and scope

The roadmap's v0.1 is a viewer someone can use every day. Today the app opens only the file named on
the command line, has no way to find anything in a document, and cannot copy text. In scope:

| Feature | What "done" means |
| :--- | :--- |
| Open | File menu and Ctrl+O with a native file dialog, drag-and-drop of a PDF onto the window, opening a second document replaces the first and frees it |
| Recent files | The last 10 opened files in the File menu, persisted across runs |
| Thumbnails | A sidebar of page thumbnails, virtualized, with the current page marked; a click goes to the page |
| Outline | The document's outline (bookmarks) as an expandable tree in the same sidebar; a click goes to the destination |
| Text search | A find bar (Ctrl+F), hits highlighted on the pages, next/previous (Enter, Shift+Enter, F3, Shift+F3), a hit counter, searched in the background without stalling scroll or render |
| Selection and copy | Drag to select text, within and across pages, highlighted; Ctrl+C copies it |
| Theme | Light, dark, or the system's, switchable and remembered; the page itself stays as the document draws it |
| Keyboard shortcuts | One table (§4.8) covering all of the above plus Plan 0002's navigation |

**Out of scope, not designed out:** clicking links inside pages (the outline's destination code is
the same, so it is a small follow-up), annotations (v0.2), printing, multiple open documents/tabs,
reflowable formats (EPUB) beyond what MuPDF already opens, OCR.

## 2. What exists and what has to change

- **The engine actor is the only owner of the `Document`** (ADR 0003, extended by Plan 0001's pool),
  and every request is a message. Open, outline and per-page text are new messages; nothing in the
  pipeline needs to change shape for them.
- **ADR 0003 is out of date**: it still describes `RenderPage` and a single rendering thread, while
  the code renders tiles on a pool. It is corrected in Phase 1 alongside the ADR for the new
  dependencies (§9 questions 1-3), and a search thread (§3.6) would be its own ADR.
- **The app has one document and no chrome**: a toolbar, a viewport and a status bar. v0.1 adds a
  menu bar, a sidebar and a find bar around the same viewport.

## 3. Phase 0 findings (verified, with evidence)

### 3.1 File dialog: Slint has none; `rfd` costs 1.5 KiB on Windows

Slint 1.18.1 ships no file dialog. The common Rust choice is `rfd` 0.17.2 (MIT): on Windows it calls
the system's COM file dialog, on macOS `NSOpenPanel`, on Linux the XDG desktop portal by default
(features `xdg-portal`, `wayland`) or GTK 3 as an option.

Measured with a throwaway crate built with this workspace's release profile (`opt-level = "z"`, fat
LTO, `panic = "abort"`, stripped) on the §1 machine (`benchmarks.md` §9.2): an empty `main` is
116,224 bytes, the same `main` calling `rfd::FileDialog::new().add_filter(..).pick_file()` is
117,760 bytes - **+1,536 bytes** on Windows, where the dialog is the operating system's. `cargo deny
check licenses bans` on that probe passes for every `rfd` dependency (the only failure was the
unlicensed probe crate itself). On Linux the default features pull `wayland-client`,
`wayland-protocols`, `quick-xml` and `pollster`; the Linux size is **not measured** (no Linux machine
here) and becomes a CI number in Phase 1.

`pick_file` is modal and blocks the calling thread until the dialog closes. On Windows it must run on
the UI thread to have an owner window; that is the normal behaviour of a modal dialog.

### 3.2 Drag-and-drop of files: not delivered by Slint 1.18.1, already written upstream

**What 1.18.1 does.** Slint's `DropArea` (`i-slint-compiler-1.18.1/builtin_elements.rs:1834-1848`,
callbacks `can-drop` and `dropped`) receives a `DataTransfer`, and `DataTransfer` already has a
stable file-path API: `has_file_paths()` and `file_paths()`
(`i-slint-core-1.18.1/data_transfer.rs:289, 335`). The docs say a `DropArea` "also accepts drops from
other applications" on platforms that support it. The winit backend - the only backend in this
build (`i-slint-backend-qt` is not in `Cargo.lock`) - does not: it never handles winit's
`WindowEvent::DroppedFile` (no occurrence in `i-slint-backend-winit-1.18.1/*.rs`), so on 1.18.1 an
external drop never reaches a `DropArea`.

**What winit 0.30 itself offers.** `DroppedFile` is emitted only by the Windows
(`winit-0.30.13/src/platform_impl/windows/drop_handler.rs`), macOS (`macos/window_delegate.rs`) and
X11 (`linux/x11/event_processor.rs`) backends; the Wayland backend has no implementation.

**Options.**

- **A - the unstable hook.** `unstable-winit-030` exposes
  `WinitWindowAccessor::on_winit_window_event` (`i-slint-backend-winit-1.18.1/lib.rs:1112-1123`),
  which sees `DroppedFile`. It means pinning `slint = "~1.18"` (`slint-1.18.1/lib.rs:677`),
  re-checking on every Slint upgrade, and **no drop on Wayland** (winit 0.30 has none).
- **B - the stable API, waiting for upstream.** The work is done upstream but not released:
  winit's new drag-and-drop API was merged on 2026-07-16 and implements receiving drops on Windows,
  macOS, **Wayland** and X11 ([rust-windowing/winit#4571](https://github.com/rust-windowing/winit/pull/4571));
  Slint's winit backend turns those drops into a `DataTransfer` with file paths
  ([slint-ui/slint#13527](https://github.com/slint-ui/slint/pull/13527), merged 2026-09-21 into the
  `feature/winit-0.31` branch). That branch reaches a Slint release only after winit 0.31 is released;
  neither date is known. A `DropArea` handler written today against `file_paths()` compiles on
  1.18.1, is inert there, and starts working on the Slint release that carries #13527 - with no
  unstable API, no pin and Wayland included. It is testable headlessly now:
  `i-slint-backend-testing` can simulate a native drop (`simulate_native_drop`,
  `testing_backend.rs:399`).
- **C - platform code of our own.** Not recommended: it means re-implementing what winit does, once
  per platform - an OLE `IDropTarget` on the native window on Windows (`unsafe` COM), an
  `NSDraggingDestination` on the `NSView` on macOS (Objective-C runtime), the XDND protocol on X11,
  and `wl_data_device` on Wayland, where the connection belongs to winit and cannot be shared. Four
  `unsafe` integrations into a window we do not own, each of which an upstream release makes
  redundant - exactly the scope §3.2 B gets for free.

**Recommendation: B.** Write the `DropArea` handler and its headless test in Phase 1; drag-and-drop
then lights up with the Slint upgrade. Until then the user opens files with Ctrl+O, the recent list,
or the operating system's "open with" (the path arrives as the command-line argument, which already
works). A is a stop-gap only if drag-and-drop is required before that Slint release.

### 3.3 Clipboard: no public API, but `arboard` is already linked

Slint's only clipboard entry points are `TextInput.copy()` and the `Platform::set_clipboard_text`
hook (`i-slint-core-1.18.1/platform.rs:142`), which application code cannot reach. `arboard` 3.6.1 is
already a runtime dependency on Windows and Linux through `i-slint-backend-winit`
(`cargo tree -i arboard -e normal`, both targets), with `default-features = false`. Depending on
`arboard = { version = "3.6", default-features = false }` directly therefore adds no new crate and
no new code beyond the calls; on Linux it needs the same `wayland-data-control` feature Slint enables.

**X11 and quitting.** On X11 the application that copied serves the clipboard until another
application takes it, so a copy would normally die with the app. arboard handles the standard way
out: when its last `Clipboard` instance is dropped it asks the X11 clipboard manager to take the
data (ICCCM `CLIPBOARD_MANAGER` / `SAVE_TARGETS`, waiting at most 100 ms;
`arboard-3.6.1/src/platform/linux/x11.rs:711-795, 1082-1096`). GNOME, KDE, XFCE and Cinnamon sessions
run a clipboard manager, so a copy survives quitting there; on a bare window manager without one it
does not, which is how every X11 application behaves.

Decision (§0): **no X11-specific code**. The one obligation is that the drop actually runs: Rust does
not guarantee that the main thread's thread-locals are destroyed at exit, so the app keeps its single
`arboard::Clipboard` outside the thread-local state and drops it explicitly after `run()` returns.
Wayland goes through the data-control protocol, whose availability depends on the compositor; that
is checked on a Wayland session in Phase 4.

### 3.4 Theme: `Palette.color-scheme`

The std widgets expose `in-out property <ColorScheme> color-scheme` on the global `Palette`
(`i-slint-compiler-1.18.1/widgets/fluent/style-base.slint:34`), with `ColorScheme.unknown` following
the system. The app's own colours (viewport background, borders, status text) are hard-coded today
and move to `Palette` brushes. The page raster is the document's content and stays as drawn; a "dark
page" inversion is a different feature and out of scope.

### 3.5 Outline, destinations, thumbnails

- `Document::outlines() -> Vec<Outline>` (`patches/mupdf/src/document.rs:266`) returns the whole tree
  at once: `title`, `uri`, `dest: Option<LinkDestination>`, `down` (`outline.rs:5-10`). A destination
  carries `Location::page_number` (absolute page, `document.rs:45-51`) and a `DestinationKind` such as
  `FitH { top }` (`destination.rs:58+`), i.e. enough to scroll to the right line of the right page
  with Plan 0002's `page_top` plus an offset.
- Thumbnails need a **virtualized list**. Slint's `ListView` lets the runtime lay out its repeater
  (`i-slint-compiler-1.18.1/passes/flickable.rs:96`), instantiating only the rows in view, so 20,000
  thumbnails cost the rows on screen. Each thumbnail is the base-layer path (Plan 0001) at a
  thumbnail scale, held in a small LRU like the viewport's base layers.
- A thumbnail of a page far from the viewport would evict a visible page's display list from the
  engine's 8-page LRU (Plan 0002 §4.3). Thumbnails should therefore rasterize **without caching** their
  display list (run the page once into a small pixmap), so the sidebar cannot thrash the viewport.

### 3.6 Search: ~1.5 ms a page, so a long document takes seconds

Measured by `crates/engine-mupdf/tests/text_bench.rs` (release, the §1 machine; `benchmarks.md`
§9.1) on generated documents of 50 lines of Helvetica a page (3,827 characters):

| Per page, steady state | Time |
| :--- | ---: |
| Load the page and extract its structured text (`to_text_page`) | ~1.1 ms |
| `TextPage::search`, a word present / absent | 0.46 / 0.43 ms |
| Walk every char of the text page | 0.011-0.014 ms |
| The first page of a process (MuPDF's one-off font/first-touch cost) | 1.1-1.8 s |

One query is therefore ~1.5 ms x pages after the first touch: **about 1.5 s for 1000 pages, ~31 s
for 20,000**, plus the first-touch second. (The per-page means the test prints include that first
page; `benchmarks.md` §9.1 separates it.) Consequences:

1. **Search cannot run on the engine actor.** Tiles are prepared there (Plan 0001); a search
   interleaved with them would stall every render request behind seconds of text extraction. The
   proposal is a **search thread with its own `Document`** opened on the same file: MuPDF contexts
   are cloned per thread already (the pool does it), and a second document is the supported way to
   use one file from two threads. Its cost is a second object cache (~1.4 KiB a page at open, Plan
   0002 / backlog item 4).
2. **Hits stream in**, page by page from the current page onwards (wrapping), so the first hit near
   the reader appears in milliseconds and the counter grows while the rest is searched.
3. **Cancellation is per page**: a new query or a closed document sets a flag checked between pages;
   `to_text_page` has no cookie, so the latency is one page's extraction (~1.1 ms here; the largest
   page of a real document bounds it, as with tiles).
4. **Text pages are not kept**: a hit list is a few quads per hit, while a text page holds every
   character's quad and font. Selection extracts the text pages it needs on demand.

These are synthetic best cases (one Type 1 base font, no compression); real documents with embedded
fonts and compressed streams will be slower, and `FA_PDF_BENCH_PDF` measures them once the
maintainer's documents arrive.

### 3.7 Selection and copy

- `TextPage::highlight_selection(a, b, quads)` (`patches/mupdf/src/text_page.rs:476`) returns the
  quads MuPDF itself would highlight between two points of a page - the selection's shape for free.
- The text of a selection is `fz_copy_selection` in C (`mupdf/include/mupdf/fitz/structured-text.h:689`),
  but **neither `mupdf-sys`' safe wrappers nor `mupdf-rs` expose it**. MuPDF reports errors by
  `longjmp`, so calling the raw binding from Rust without a C `fz_try` wrapper is undefined behaviour.
  Two ways (§9 question 5): build the text in Rust from the text page's chars in reading order between
  the two points (the char walk is 0.014 ms a page), or vendor `mupdf-sys` next to `mupdf` under
  `patches/` and add a `mupdf_copy_selection` wrapper.
- **Dragging pans today.** The `Flickable` has `mouse-drag-pan-enabled`
  (`i-slint-compiler-1.18.1/builtin_elements.rs:1505`), which turns mouse-drag panning off while
  touch panning stays (`flickable.rs:248-252`). That is exactly the split §0 decided: mouse selects,
  touch pans.
- **Mouse and touch are told apart** by `PointerEvent.touch_finger_id`, 0 for a mouse
  (`i-slint-common-1.18.1/builtin_structs.rs:86`).
- **Long press is not a Slint event**; it is a 500 ms `Timer` started on a touch `down`, cancelled by
  `up` or by moving more than a few pixels. When it fires, the word under the finger is selected and
  the `Flickable` is made non-`interactive` until the finger lifts, so the drag extends the selection
  instead of panning. No touchscreen is available here, so touch behaviour is a manual check.

### 3.8 Recent files and settings: no new dependency

`dirs` is in `Cargo.lock` but not in the app's runtime graph on Windows, and `serde`/`toml` only
appear in Slint's build-time macros. The settings directory is a few lines of `std::env`
(`%APPDATA%` on Windows, `$XDG_CONFIG_HOME` or `~/.config` on Linux, `~/Library/Application Support`
on macOS) and the file is plain text - one `key=value` per line, recent paths as `recent=<path>` - so
no parser is needed. A missing or unreadable file means defaults, never an error dialog.

## 4. Design

### 4.1 Engine protocol additions (`core`)

| Command | Event | Thread |
| :--- | :--- | :--- |
| `Open { path }` (exists) - now also on a running app | `Opened`, then `Outline { items }` | actor |
| `RenderThumb { page, width_px, request_id }` | `ThumbRendered { page, bitmap }` | pool, display list not cached (§3.5) |
| `Search { query, from_page, generation }` | `SearchHits { page, quads, generation }` then `SearchDone { generation, pages }` | search thread (§3.6) |
| `CancelSearch { generation }` | - | search thread |
| `SelectText { a: (page, pt), b: (page, pt), generation }` | `Selection { per-page quads, text, generation }` | search thread (it has the second document and is idle unless searching) |

`Outline { items }` is a flattened tree (`depth`, `title`, `page`, `top`), so the app needs no
recursion and the list can feed a `ListView` directly.

### 4.2 Open, replace, close

Opening while a document is open: the app begins an epoch, releases every row and base layer
(Plan 0002 already does this in `set_document`), and the actor drops the old `Document` before
opening the new one; the search thread does the same on its next command. Acceptance: opening the
same 20,000-page file ten times leaves the working set within 10 MiB of opening it once.

### 4.3 Sidebar

A left panel (toggle F4, Ctrl+B) with two tabs, Thumbnails and Outline, each a `ListView`. Thumbnails
are 160 logical px wide, rendered when their row is instantiated and kept in an LRU of 64; the
current page's row is highlighted and kept in view as the reader scrolls. The outline flattens the
tree with an indent per depth and collapse/expand per node.

### 4.4 Find bar and highlights

Ctrl+F opens a bar above the viewport. Typing starts a search after a short debounce (200 ms);
Enter/F3 next, Shift+Enter/Shift+F3 previous, Esc closes and clears. Hits on pages near the viewport
are drawn as translucent rectangles from their quads (page-relative, placed with `DocLayout` like
tiles), the current hit in a stronger colour, and moving to a hit scrolls it into view. The counter
reads "3 of 41" while searching continues ("3 of 41+").

### 4.5 Selection

In the select tool, a drag starts at a page point and ends at another, possibly on another page;
the app asks the search thread for the quads and text of every page from the first to the last,
draws the quads like search hits, and keeps the text for Ctrl+C. Double-click selects a word,
triple-click a line (both from the char walk). The cost of a selection across many pages is one text
page per page in it, bounded by the selection's length.

### 4.6 Theme

`Palette.color-scheme` set from the setting (`system` → `ColorScheme.unknown`), every colour in the
app taken from `Palette` brushes instead of hex literals, and a View menu entry to switch.

### 4.7 Settings and recent files

One plain-text file (§3.8), written whenever a document opens or the theme changes, at most 10
recent entries, newest first, missing files dropped when the menu is built.

### 4.8 Keyboard shortcuts

| Keys | Action |
| :--- | :--- |
| Ctrl+O | Open |
| Ctrl+F | Find |
| Enter / Shift+Enter, F3 / Shift+F3 | Next / previous hit |
| Esc | Close the find bar, clear the selection |
| Ctrl+C | Copy the selection |
| F4, Ctrl+B | Toggle the sidebar |
| (Plan 0002) arrows, PgUp/PgDn, Space, Home/End, Ctrl +/-/0, ctrl+wheel | Navigation and zoom |

## 5. Phases

Each phase is shippable on its own and ends at a gate.

### Phase 1 - Open, recent files, theme

Menu bar (File: Open, Open Recent, Quit; View: Theme), Ctrl+O, the file dialog, drag-and-drop
(by §9 question 2's answer),
replacing a document, the settings file, the theme. ADRs for the new dependencies, ADR 0003 brought up
to date. **Acceptance:** §6 rows H-I.

### Phase 2 - Sidebar: thumbnails and outline

`RenderThumb` without display-list caching, the virtualized thumbnail list, `Outline`, the outline
tree, navigation from both. **Acceptance:** rows J-K.

### Phase 3 - Search

The search thread with its own document, streaming hits, cancellation, the find bar, highlights,
next/previous. **Acceptance:** rows L-M.

### Phase 4 - Selection and copy

Mouse selects by default, touch pans and selects on a long press (§3.7); `highlight_selection`, the
selection text built in Rust, Ctrl+C through `arboard`, multi-page selection, double/triple click.
In parallel, a pull request to mupdf-rs adding a safe `copy_selection` (a C wrapper with
`fz_try`/`fz_catch` in `mupdf-sys` and the Rust method), linked from this plan; if it is merged and
released, the app switches to it. **Acceptance:** row N.

## 6. Acceptance and benchmarks

Metric definitions go into `benchmarks.md` §9.3 before any is measured (done in this phase).

| Row | Scenario | Pass |
| :--- | :--- | :--- |
| H | Open the 20,000-page synthetic document 10 times in one process | `ws` after the tenth open within 10 MiB of after the first |
| I | Settings | Recent files and theme survive a restart; a corrupt or missing settings file opens with defaults; unit-tested |
| J | Scroll the thumbnail list from page 1 to 20,000 | Thumbnail memory bounded by the LRU (`thumbs_resident` <= 64); the viewport's `t_blank` verdict unchanged while thumbnails render |
| K | Outline | Every entry of a test document's outline lands on its page (scripted, like `--bench-nav`) |
| L | Search 1000 text pages for a word on every page | first hit <= 50 ms after the debounce (`t_first_hit`); whole document within 2x §3.6's per-page cost; scrolling during the search keeps Plan 0001's `t_blank` verdict |
| M | Cancel | A new query cancels the old one within one page's extraction; no hit of an old generation is ever shown (`core` test plus a mutation check) |
| N | Selection | Copied text of a selection across three pages equals the expected text of a generated document, byte for byte |
| O | Memory after search | `ws` before a search, right after a full search of the 20,000-page text document, and 10 s later, with the search thread's document kept open; reported as `ws_after_search` |

## 7. Risks

| Risk | Impact | Mitigation |
| :--- | :--- | :--- |
| `unstable-winit-030` changes in a Slint minor release | Drag-and-drop breaks on upgrade | Pin `~1.18`; it is isolated in one function; without it, Open still works |
| Real documents search far slower than §3.6 | Long searches | Streaming hits and per-page cancellation make it responsive regardless; real numbers when the maintainer's documents arrive |
| A second `Document` doubles the per-page open cost | Memory | ~1.4 KiB a page (27 MiB at 20,000 pages); measured in row H's setup; backlog item 4 may reduce both |
| Rust-built selection text differs from MuPDF's in reading order | Wrong copied text on complex layouts | Row N on a generated document; the vendored-wrapper option stays available |
| Thumbnails compete with viewport tiles for the pool | Slower viewport | Thumbnails queued after tiles and never cached as display lists; row J checks `t_blank` |

## 8. Deliberate non-goals

- **No links inside pages** in v0.1 (follow-up, shares the outline's destination code).
- **No tabs or multiple windows**: one document at a time.
- **No search options** beyond MuPDF's default (case-insensitive); whole-word and regex later.
- **No dark-page rendering** (inverting page colours).

6. **Default mouse tool:** select text by default (drag selects, wheel/scrollbar/keys scroll, touch
   still pans; recommended, as browsers and most viewers do), or hand by default with a select toggle?
7. **Phase order:** 1 Open/recent/theme, 2 sidebar, 3 search, 4 selection - or another order?
