## 1. Goal and scope

The roadmap's v0.3 (maintainer's decision, 2026-10-22): organize a document's pages, and the
everyday "iLovePDF-style" tools, without leaving the app.

| Feature | What "done" means |
| :--- | :--- |
| Rotate, delete, duplicate, move pages | From the thumbnail sidebar (one or several selected pages) and the menu; each is one undo step |
| Insert pages | A blank page, or pages from another PDF, before or after a chosen page |
| Merge | Several PDFs into one new document, in a chosen order |
| Split, extract | A page range, every N pages, or the selected pages into new files |
| Metadata | Title, author, subject and keywords viewed and edited |
| Watermark, page numbers | Text on every page (or a range): position, size, colour, opacity; page numbers with a format such as "{n} / {total}" |
| Crop | A crop box drawn on a page, applied to it or to all pages |
| Compress | A smaller copy: lossless (object and stream clean-up) and lossy presets (images downsampled and recompressed) |
| PDF to images, images to PDF | Pages to PNG or JPEG at a chosen resolution; PNG and JPEG files to a new PDF, one per page |
| Save a repaired copy | A document MuPDF had to repair at open says so and offers a clean full copy |
| PDF to Word | Only if §9 question 6 says so, after the maintainer has judged real conversions (§3.6) |

**Out of scope, not designed out:** Office to PDF (it needs LibreOffice-class dependencies, against
the resource priority), OCR (roadmap "Later"; MuPDF's Tesseract is already compiled in, §3.6),
editing page content, outline (bookmark) editing, PDF/A conversion, forms (v0.4), redaction and
encryption (v0.5).

## 2. What exists and what has to change

- **Page count and order are fixed today.** The layout (`pdf_core::DocLayout`), the per-page
  revisions (Plan 0004 §4.1), thumbnails, text lines, annotations, search hits, the outline's
  targets and the selection are all keyed by page index, built once at open. A structural edit
  changes indices, so every one of them has to be rebuilt or remapped (§4.1).
- **Every edit is one journal operation** (`EngineCmd::Edit`, ADR 0008), and the engine's history
  records the page each step changed (`history: Vec<u32>`). A structural step changes no single
  page; the history has to say so, so that undo and redo rebuild the layout too.
- **One engine actor thread** runs every command. The fast operations (§3.3: milliseconds) can run
  there; the slow ones (compressing images: seconds) would freeze rendering, so they need their
  own thread on their own document (§4.2).
- **Save As writes a full copy and reopens it** (`crates/engine-mupdf/src/lib.rs`, `save`); the
  undo history starts again from the copy.

## 3. Phase 0 findings (verified, with evidence)

Measurements: `crates/engine-mupdf/tests/tools_bench.rs` and `docx_bench.rs`, release build,
2026-10-22, the `benchmarks.md` §1 machine; numbers in `benchmarks.md` §11.

### 3.1 mupdf-rs 0.8 covers the page operations, as journal steps

The vendored mupdf-rs (`patches/mupdf`) has, for `PdfDocument`:

| Operation | API |
| :--- | :--- |
| Insert pages from another PDF (merge) | `insert_pdf(src, InsertPdfOptions)` (`src/pdf/document.rs:1259`) |
| Duplicate, copy | `copy_page`, `duplicate_page` (`:1297`, `:1318`) |
| Move | `move_page` (`:1322`) |
| Delete | `delete_pages(selection)` (`:1357`) |
| Keep only some (split into a copy) | `select_pages(selection)` (`:1378`) |
| Page labels | `set_page_label_rule` (`:1413`) |
| Blank page | `new_page_at(index, size)` (`:897`) |

and for `PdfPage`: `set_rotation` (`src/pdf/page.rs:1835`), `set_crop_box` (`:1891`),
`insert_contents` (`:992`), `insert_font` (`:1747`), `insert_image` (`:806`).

Each of the document operations runs inside a `DocOperation` (`src/pdf/mod.rs:46-64`): MuPDF's
`begin_operation` / `end_operation`, `abandon_operation` on failure. With the journal on, each is
one undo step, and nested inside an outer operation they join it: rotating 200 pages in one outer
operation is one step, undone in 0.01 ms (§11.1).

### 3.2 Gaps in mupdf-rs 0.8, all present in MuPDF 1.27.2

| Need | MuPDF function | In mupdf-rs 0.8 |
| :--- | :--- | :--- |
| Lossy compression: downsample and recompress images | `pdf_rewrite_images` (`include/mupdf/pdf/image-rewriter.h:83`) | no |
| JPEG export | `fz_save_pixmap_as_jpeg` (`include/mupdf/fitz/write-pixmap.h:242`) | no: `ImageFormat` is PNG, PNM, PAM, PSD, PS (`src/pixmap.rs:12`) |
| Writing metadata | `fz_set_metadata` (`include/mupdf/fitz/document.h:960`) | read only: `Document::metadata` (`src/document.rs:112`) |
| Closing a document writer safely | `fz_close_document_writer` | called outside `fz_try` in `Drop` (`src/document_writer.rs:69-78`): an error there unwinds through Rust (undefined behaviour) |

They throw, so each needs the same kind of `fz_try` wrapper as the journal (ADR 0008,
`patches/mupdf/journal/journal.c`), against the same vendored headers, plus an upstream pull
request. GitHub code search finds none of them in mupdf-rs `main` (2026-10-22). Metadata could
instead be written through the trailer's `/Info` dictionary with the existing `PdfObject` API, at
the cost of the XMP stream staying stale. §9 question 4.

### 3.3 Cost of the operations

On a generated 200-page text document (`benchmarks.md` §11.1):

| Operation | Time |
| :--- | ---: |
| Move a page | 0.49 ms (undo 0.01 ms) |
| Rotate all 200 pages, one step | 4.0 ms (undo 0.01 ms) |
| Delete 100 pages | 1.4 ms |
| Duplicate a page | 0.06 ms |
| Crop all 200 pages | 4.4 ms |
| Merge 200 + 200 pages | 39.6 ms, full save 53.6 ms |
| Split 10 pages into a new file | 1.3 ms |
| Watermark and page number on 200 pages, one step | 13.5 ms (0.068 ms per page) |
| Lossless compress, 540 KiB text document | 23 ms, to 77 KiB |
| Lossless compress, 10 image pages (60 MiB, see §3.5) | 1.9 s, to 2.4 MiB |
| PNG export at 150 dpi | 150 ms per page, 251 KiB per page |

Everything that changes the open document is far below a frame; only the conversions take long
enough to need a thread and a progress indication (§4.2).

### 3.4 A garbage-collecting save breaks undo on the open document

`a_garbage_collecting_save_breaks_undo` (`tools_bench.rs`): after a full save with
`garbage` (object clean-up, what "compress" means losslessly), MuPDF's journal still steps back -
`undo` returns success and the position moves - but the page keeps the change. A full save
without garbage collection, a compressed one without it, and an incremental save all leave undo
working.

So **no tool may garbage-collect the open document.** Compress, and anything else that rewrites
objects, writes from a separate document (the file, or the open document's current state written
to memory first) and leaves the open one alone. The engine's in-place save is incremental and its
Save As writes without garbage collection and reopens, so v0.2 is not affected.

### 3.5 New pages' streams are stored uncompressed by a plain save

Ten PNG pages placed with `insert_image` and saved with the default options: **60.2 MiB**; the same
document saved with `compress` and garbage collection: 2.4 MiB. MuPDF keeps new streams
uncompressed unless the save asks otherwise. Every tool that writes a new file must save with
`compress` (and `compress_images`, `compress_fonts`); the incremental in-place save of an edited
document should compress its new streams too (§4.3).

### 3.6 PDF to Word: already built in, quality to be judged on real documents

- **Build:** mupdf-rs' default features include `docx-output` - and `js`, `tesseract`, `html`,
  `epub` and others (`patches/mupdf/Cargo.toml:55-68`). MuPDF's DOCX writer (the `extract`
  library) is therefore compiled today; the linker leaves it out only because nothing calls a
  document writer. A binary that uses `DocumentWriter` grows by **2.48 MiB** (all of MuPDF's
  writers come together, selected at run time by name); the DOCX writer's own share is **0.23 MiB**
  (the same test binary built with `docx-output` turned off: 10.40 against 10.64 MiB).
- **Output** (`docx_bench.rs`): text is kept and in reading order. Each page of the generated
  documents becomes one paragraph: the 50 lines of a page are joined with spaces, without line or
  page breaks. That is right for prose and wrong for lists, tables and forms; the generated
  documents have neither, so they cannot decide the question.
- **Time:** 3.7 ms per page on 400 text pages; 1.4 s for the first, three-page document (a
  one-time start-up of the writer).
- **To decide:** the maintainer converts real documents (letters, reports, a table, two columns,
  Turkish text) with
  `FA_PDF_DOCX_INPUT=path cargo test --release -p engine-mupdf --test docx_bench -- --ignored --nocapture`
  and opens the `.docx` files in a word processor. §9 question 6.

Separately: `tesseract` (OCR) and `js` are compiled in by the same default features without the
app using them (`docs/backlog.md` item 11).

### 3.7 What Slint 1.18 offers for organizing pages

- **Drag to reorder:** `DragArea` (with a drag image) and `DropArea`
  (`i-slint-compiler-1.18.1/builtin_elements.rs:1779`, `:1832`). Drops from other applications
  never arrive with the winit backend (Plan 0003 §3.2), but a drag inside the window is Slint's own.
  Not yet tried; whether a long press starts a drag on touch is unverified. Phase 1 starts with
  that check, and buttons (move earlier / later) remain either way.
- **Dialogs:** the tools' options (range, format, preset) are small Slint panels like the note
  editor; files are chosen through `rfd` (ADR 0004), which can pick several files for a merge.

## 4. Design

### 4.1 Structural edits

New `EditOp` variants: `RotatePages { pages, by }`, `DeletePages { pages }`,
`DuplicatePages { pages }`, `MovePages { pages, to }`, `InsertBlank { at, size }`,
`InsertFrom { path, pages, at }`, `Crop { pages, rect }`, `Stamp { pages, stamp }`,
`SetMetadata { fields }`. Each is one journal operation, like the annotation edits.

- **Engine:** after a structural step (and its undo or redo) it sends
  `Restructured { generation, page_sizes, map }` instead of `PageChanged`: the new page sizes and,
  for every new page, the old index it came from (or none). The history records the step as
  structural.
- **App:** the layout is rebuilt from `page_sizes`; the scroll position stays on the same page
  (followed through `map`); tiles, revisions, thumbnails, text lines and annotations of moved pages
  are remapped through `map`, the rest dropped and asked for again; the outline is reloaded (its
  targets are page objects in the file, so MuPDF resolves them to the new indices); search results
  and the selection are cleared.
- Rotation and crop change page sizes but not indices: they bump the page's revision and its size,
  and the layout is rebuilt.

### 4.2 Tools that write new files

Merge, split, extract, export to images, images to PDF, compress, the repaired copy and DOCX run on
a **tool thread** with their own `PdfDocument`, never on the open one (§3.4):

- The source is the open document's current state, written to memory (`write_to`, no garbage
  collection) when it has unsaved changes, or the file when it has none. §9 question 3.
- Progress is reported per page; a Cancel stops between pages and deletes the partial output.
- Outputs are saved with compression (§3.5); a new document can be opened right away.

### 4.3 Compression presets

| Preset | What it does |
| :--- | :--- |
| Lossless | Garbage collection, streams, fonts and images compressed losslessly |
| Balanced | Lossless, plus colour and grey images above 225 dpi downsampled to 150 dpi as JPEG, quality 75 |
| Strong | Images above 150 dpi to 96 dpi, JPEG quality 60 |

The lossy presets need `pdf_rewrite_images` (§3.2). Each run reports the size before and after and
keeps the original when the result is not smaller.

The engine's in-place save (Plan 0004) gains `compress` for new streams, so an image placed by a
v0.3 tool does not grow the file by its raw size (§3.5).

### 4.4 UI

- **Sidebar, Pages tab:** click, Ctrl+click and Shift+click select thumbnails; a strip above them
  rotates left or right, duplicates, deletes and extracts the selection; dragging moves it (§3.7);
  right-click offers the same and "Insert blank page" / "Insert from file...".
- **Tools menu:** Merge files..., Split..., Watermark..., Page numbers..., Crop..., Compress...,
  Export as images..., Images to PDF..., Document properties..., and (§9 question 6) Export as
  Word.
- **Crop:** a Crop tool draws the rectangle on the page, with "this page" or "all pages".
- **Repaired documents:** when MuPDF repaired the file at open, the status bar says so and offers
  "Save repaired copy..." (Plan 0004 already sends such files to Save As for saving).
- Every tool that changes the open document is undoable and marks it unsaved, as annotations do.

## 5. Phases

### Phase 1 - Page structure

`Restructured`, the layout rebuild and remapping (§4.1); rotate, delete, duplicate, move and insert
a blank page from the sidebar (selection, strip, drag or buttons) and the menu; undo and redo of
each; the in-place save compresses new streams. Starts with the drag-on-touch check of §3.7.
**Acceptance:** rows AA, AB, AG.

### Phase 2 - Merge, split, insert, extract, metadata

The tool thread and its progress (§4.2); Merge files, Split, Extract pages, Insert from file;
Document properties. **Acceptance:** rows AC, AG.

### Phase 3 - Stamps and crop

Watermark, page numbers and crop, each one undo step. **Acceptance:** row AD.

### Phase 4 - Convert

Export as PNG and JPEG, images to PDF, compress with its presets, the repaired copy; the `fz_try`
wrappers of §3.2 with their upstream pull request. **Acceptance:** rows AE, AF.

### Phase 5 - PDF to Word

Export as Word on the tool thread (§0, question 6). **Acceptance:** row AH.

## 6. Acceptance and benchmarks

Metric definitions are added to `benchmarks.md` §11.2 before the phase that measures them.

| Row | Scenario | Pass |
| :--- | :--- | :--- |
| AA | Page operations round trip | On 200 pages: rotate, delete, duplicate, move and insert blank, each one undo step; undoing all restores every page's first text line, rotation and size; redoing all and saving in place reopens equal; a mutation check (a step outside the journal) makes it fail |
| AB | Structural edit latency | `t_restructure` (command sent to every visible tile of the new layout shown) <= 100 ms on 200 and 1000 pages; the scroll position stays on its page |
| AC | Merge and split | Merged page count and first lines equal the inputs in order, links and annotations kept; split outputs' pages equal the source range; outputs open in another reader (manual) |
| AD | Stamps | Watermark and page number text extractable on every page, one undo step, <= 1 ms per page; crop changes the page size seen by the layout |
| AE | Compress | Lossless never larger than the input; Balanced at least halves a scanned (image) document; the open document's undo still works after a compress (the §3.4 trap, mutation-checked) |
| AF | Images | PNG export at 150 dpi <= 300 ms per page; images to PDF stored compressed (output <= 1.2 x the input files) |
| AG | Memory | `ws` after merging 1000 + 1000 pages and after 100 structural edits, reported |
| AH | Word | Maintainer's judgement on real documents (§3.6) |

Each phase also runs the suite on the Android phone (`docs/backlog.md` item 9).

## 7. Risks

| Risk | Impact | Mitigation |
| :--- | :--- | :--- |
| A tool garbage-collects the open document | Undo silently does nothing (§3.4) | Tools write from a separate document (§4.2); row AE's mutation check |
| Remapping misses a per-page cache after a structural edit | Wrong page drawn or selected | One `map` used by every cache; row AA's round trip through the window |
| Slow tools on the engine thread | Rendering freezes | The tool thread (§4.2) |
| A `fz_try` shim that grows | More code we own until upstream | Same pattern and header check as ADR 0008; upstream pull requests; removed with the release (`backlog.md` item 10) |
| Closing a document writer throws | Undefined behaviour | The writer is closed through a wrapper (§3.2) before it is dropped |
| Drag does not start on touch | No drag-reorder on phones | Move buttons in the strip (§3.7) |

## 8. Deliberate non-goals

- **No Office to PDF** (§1), **no OCR** in v0.3.
- **No editing of page content** (text or images on the page).
- **No outline editing**: moved pages keep their outline entries, deleted pages' entries point
  nowhere.
- **No batch processing of many files** beyond merging.
