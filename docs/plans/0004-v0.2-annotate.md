## 1. Goal and scope

The roadmap's v0.2 makes the viewer an annotator: someone reads a PDF, marks it up, saves it, and
another PDF reader shows the same marks.

| Feature | What "done" means |
| :--- | :--- |
| Existing annotations | Annotations already in a document are drawn on the pages and thumbnails, as other readers draw them (§3.1: today they are not) |
| Text markup | Highlight, underline, strike-out (and squiggly, which costs nothing extra) made from a text selection, in a chosen colour |
| Notes | A sticky note (PDF `Text` annotation) placed on a page, its text written and edited in the app, shown on hover |
| Ink | Free-hand strokes with the mouse, pen or a finger, in a chosen colour and width |
| Select, recolour, delete | Clicking an annotation selects it; Delete removes it; its colour can be changed. This covers annotations the document already had |
| Save | Ctrl+S saves in place incrementally; Save As writes a full copy; the title marks unsaved changes; quitting or opening another file with unsaved changes asks first |
| Undo / redo | Ctrl+Z / Ctrl+Y (Ctrl+Shift+Z) over every edit above, across saves |

**Out of scope, not designed out:** free-text boxes (`FreeText`), shapes (lines, rectangles,
circles, polygons), stamps, moving or resizing markup and ink, replies and review states, an
annotation list panel, importing/exporting annotations (XFDF), and anything for non-PDF documents
(PNG, EPUB and the other formats MuPDF opens are view-only: the tools and Save are disabled).

## 2. What exists and what has to change

- **The engine actor owns one `mupdf::Document`** (ADR 0003). Editing needs it as a
  `mupdf::pdf::PdfDocument` (`PdfDocument::try_from(Document)`, `patches/mupdf/src/pdf/document.rs:1878`),
  which fails for non-PDF formats - that is the view-only case of §1.
- **Display lists are cached per page** (8-page LRU, `crates/engine-mupdf/src/lib.rs:127-137`) and
  tiles are keyed by page, cell and scale (`TileKey`, `crates/core/src/tiling.rs:105`). An edit
  changes one page, so that page needs a **revision**: its display list is dropped and its tiles,
  base layer and thumbnail are re-rendered, without blanking the page while the new tiles arrive.
- **The search thread has its own `Document`** (ADR 0005). Annotations do not change a page's text,
  so it needs nothing until a Save As switches the file.
- **There is no undo machinery.** `CLAUDE.md` §2 lists an "undo `Command` trait" in `core`; it does
  not exist (no `Command` type in `crates/core/src`). §3.4 is about what replaces it.

## 3. Phase 0 findings (verified, with evidence)

### 3.1 The viewer does not draw annotations today

Every display list is built with `page.to_display_list(false)` (`crates/engine-mupdf/src/lib.rs:348,
443` and the cached path), and `false` means `fz_new_display_list_from_page_contents`
(`mupdf-sys-0.8.0/wrapper/page.c:57-67`): the page's content stream without its annotations.
Highlights, notes, stamps and form-field appearances that a document already has are therefore
invisible in v0.1. Measured (`benchmarks.md` §10.1): the pixel under a highlight is grey text from
the contents-only list and yellow-tinted from the full list; building the full list costs the same
on pages without annotations (0.286 vs 0.290 ms a page). The fix is the `true` argument plus tests;
§9 question 1 asks when. **Fixed** after the gate's answer (§0): one constant, `DRAW_ANNOTATIONS`
in `crates/engine-mupdf/src/lib.rs`, drives the display lists and the full-page render;
`crates/engine-mupdf/tests/annotation_render_test.rs` checks a highlight in a tile, the full-page
render and a thumbnail, and fails with the constant set to `false` (mutation check, 2026-10-21).

### 3.2 mupdf-rs 0.8 covers creating and editing what v0.2 needs

On `PdfPage` (`patches/mupdf/src/pdf/page.rs`): `add_highlight_annotation`, `add_underline_annotation`,
`add_squiggly_annotation`, `add_strikeout_annotation` (quads, 385-411), `add_text_annotation` (rect,
contents, 275), `add_ink_annotation` (strokes, 358), `delete_annotation` (450) and `annotations()`
(466). On `PdfAnnotation` (`patches/mupdf/src/pdf/annotation.rs`): `r#type`, `xref`, `bounds`,
`rect`, `quad_points`, `ink_list`, `color`/`set_color`, `opacity`/`set_opacity`,
`contents`/`set_contents`, `author`/`set_author`, `border_width`/`set_border_width`, `flags`, and
`update()` to regenerate the appearance stream (361). All go through mupdf-sys' `fz_try` wrappers.

Costs (§10.1): creating a highlight with its appearance 0.14 ms, a 200-point ink stroke 0.12 ms, a
note 0.02 ms; an edit plus the page's display-list rebuild 0.79 ms. Editing is not a performance
problem; the latency the user sees is the page's tiles re-rendering, measured as `t_edit` (§10.2).

**Concurrency.** The pool's workers replay display lists while the actor would edit the same
document. Measured: 600 edits with rebuilt lists while three workers rendered untouched pages - no
crash, and every render pixel-identical to one taken before any edit (§10.1). A display list is a
snapshot, so tiles of the old revision stay correct for the old revision; the revision keeps them
from being shown as the new one.

### 3.3 Saving: in place works incrementally, a rename over an open file does not (Windows)

Measured on Windows (§10.1), with the edited document **and** a second `Document` on the same file
open, as the app has (actor + search thread):

- **Incremental save to the same path works**: 9.6 ms, then 5.2 ms for a second one; the file
  grows by what changed (+7.5 KB, then +649 bytes) and the original bytes stay byte-identical as a
  prefix. Both open documents still read every page afterwards (the second sees the old revision).
- **A full save to another path works** (15.4 ms for 2.8 MB).
- **Replacing the open file by a rename fails** (`os error 5`), because MuPDF holds the file open.
  The usual "write a temporary file, rename it over the original" therefore needs both documents
  closed first and reopened after.
- **`has_unsaved_changes()` stays `true` after an incremental save**, so the app cannot use it as
  its dirty flag; it keeps its own (the undo position at the last save, §3.4).

What this means for the design (§4.4):

- **Save (Ctrl+S) appends** an incremental update to the open file. It is how Acrobat saves; it
  keeps existing digital signatures valid (v0.5 cares), and the previous revision is always still in
  the file. It is not atomic: a crash during the few milliseconds of the append can leave a damaged
  tail, which MuPDF's repair recovers to the previous revision; §9 question 3 offers the atomic
  alternative and its cost.
- **Save As** writes a full copy to the new path, then the app switches to the new file (reopening
  it in the actor and the search thread, keeping the view position and the undo history's meaning:
  §3.4).
- When incremental saving is impossible (`can_be_saved_incrementally()` false, e.g. a file MuPDF
  repaired at open), Save becomes Save As.
- Appending to an open file is ordinary on Linux and macOS, but it is **untested there**; Phase 1
  adds a non-ignored test of the in-place save so CI checks it on all three platforms.

### 3.4 Undo and redo: MuPDF has a journal, mupdf-rs does not expose it

MuPDF has an undo journal on `pdf_document` (`mupdf/include/mupdf/pdf/object.h:380-438`):
`pdf_enable_journal`, operations bracketed by `pdf_begin_operation` / `pdf_end_operation`,
`pdf_undo`, `pdf_redo`, `pdf_can_undo`, `pdf_can_redo`, `pdf_undoredo_state`. It records every
object an operation changes, so it undoes any edit - annotations now, page operations (v0.3) and
form filling (v0.4) later - and a save after an undo writes the undone state.

mupdf-sys 0.8.0 wraps only `begin`/`end`/`abandon_operation` (`wrapper/pdf_document.c:317-330`),
and mupdf-rs uses them for its page operations (`DocOperation`, `document.rs:1272-1375`). The rest is
only a raw binding, and `pdf_undo`/`pdf_redo` throw (e.g. "nothing to undo"), so calling them from
Rust is undefined behaviour - the same reason as `fz_copy_selection` in Plan 0003. Upstream has no
wrapper: messense/mupdf-rs#267 proposed exactly this and was closed unmerged by its author ("opened by
mistake"), and no release since 0.8.0 (2026-06-22) has one.

Options (§9 question 2):

- **A - MuPDF's journal through a small `fz_try` shim of our own, plus an upstream PR.**
  `patches/mupdf` is already our vendored copy of the crate; it gains a `build.rs` compiling one C
  file of seven `TRY_CATCH` wrappers (the same macro mupdf-sys uses, `wrapper/internal.h`) against
  MuPDF 1.27.2's headers (968 KiB, vendored with it; the library itself stays mupdf-sys'), and
  `PdfDocument::enable_journal / undo / redo / can_undo / can_redo / undo_redo_state`. A test asserts
  the vendored headers' `FZ_VERSION` equals `mupdf_sys::FZ_VERSION`, and `patches/mupdf` pins
  `mupdf-sys = "=0.8.0"`, so a mismatch cannot build silently. The same wrappers go upstream as a PR;
  when a release has them, the shim and the headers are deleted. `cc` is already in `Cargo.lock`.
- **B - undo in Rust.** A `core` command stack where each edit knows its inverse (create <-> delete,
  old colour <-> new colour). No C, but every future kind of edit needs its own inverse, and undoing
  the deletion of an annotation the document already had means recreating it from a copy of its
  dictionary and appearance stream, which mupdf-rs has no safe way to re-attach to a page.
- **C - mupdf-sys from a git fork** with the wrappers, via `[patch.crates-io]`. Same journal as A,
  but `deny.toml` must allow a git source, and every build clones MuPDF's source as a submodule
  (the crate is 14 MB compressed, 65 MB unpacked).

**Recommendation: A.** It is MuPDF's own, already-correct undo for every kind of edit v0.2-v0.4 adds;
the code we own is seven wrappers in a macro; and it disappears once upstream has it.

### 3.5 What Slint offers for the tools

- **Live ink**: a `Path`'s `commands` may be a run-time string (`i-slint-compiler-1.18.1/passes/compile_paths.rs:63-65`),
  so the stroke being drawn is one `Path` whose SVG commands the app rebuilds on each pointer move;
  the cost is `ink_rebuild_ms` (§10.2). The committed stroke is drawn by MuPDF in the tiles like any
  annotation.
- **Note editor**: the std widgets' `TextEdit` (`widgets/fluent/textedit.slint:8`) in a panel placed
  next to the note.
- **Dialogs**: `rfd` 0.17.2 has `FileDialog::save_file` (`file_dialog.rs:172`) and a
  `MessageDialog` with `MessageButtons::YesNoCancel` (`message_dialog.rs:167`) for "save changes?".
- **Quitting with unsaved changes**: `slint::Window::on_close_requested` returning
  `CloseRequestResponse::KeepWindowShown` (`i-slint-core-1.18.1/api.rs:458-464, 530`).
- **Pen pressure**: Slint 1.18 reports no pressure, so ink has a fixed width.

## 4. Design

### 4.1 Engine protocol additions (`core`)

| Command | Event | Notes |
| :--- | :--- | :--- |
| `Annotations { page, generation }` | `Annotations { page, revision, items }` | `items`: id (the annotation's xref), kind, rect, quads or ink bounds, colour, a contents preview, whether it is editable. Asked for the pages near the view, like text lines (Plan 0003 Phase 4) |
| `Edit { op, edit_id }` | `Edited { edit_id, pages, result }`, then `Annotations` and `PageChanged { page, revision }` for each changed page | `op`: `AddMarkup { page, kind, quads, colour }`, `AddNote { page, at, contents }`, `AddInk { page, strokes, colour, width }`, `Delete { page, id }`, `SetColour`, `SetContents`, `MoveNote` |
| `Undo`, `Redo` | as `Edited` | Phase 2 |
| `Save { path: Option<PathBuf> }` | `Saved { path, result, bytes }` | `None` = in place, incremental |

Every edit is one journal operation (Phase 2) and bumps the page's revision. The actor drops the
page's display list; the app keeps the old tiles on screen and requests the page's visible tiles at
the new revision, swapping each in as it arrives (`stale_tiles` = 0, §10.2); the base layer and the
thumbnail follow. Tiles carry the revision they were rendered from, and a tile of an older revision
is never shown over a newer one.

### 4.2 Tools and input

A tool strip in the toolbar: **Select** (today's behaviour), **Highlight**, **Underline**,
**Strike-out**, **Note**, **Ink**, and a colour choice (six fixed colours; highlight opacity is
MuPDF's default multiply blend).

- **Markup** (§9 question 4): with text selected, choosing Highlight/Underline/Strike-out (button or
  shortcut) marks the selection, one quad per selected line, which `pdf_core::select` already
  computes; with a markup tool active and nothing selected, a drag selects and marks on release.
- **Note**: a click places a note icon; its editor opens at once; a double-click reopens it; hovering
  shows its text.
- **Ink**: a drag draws (mouse, pen and finger alike - touch does not pan while Ink is active);
  points are kept in page space and simplified (Ramer-Douglas-Peucker, 0.5 pt) in `core` before
  being committed on release.
- **Select**: a click (no drag) on an annotation selects it and shows its bounds; Delete removes it;
  the colour choice recolours it; a drag still selects text, as now. Esc returns to Select.

### 4.3 Author

PDF annotations carry an author (`/T`). §9 question 5: write none unless the user sets a name in the
settings file, or default to the operating system's user name.

### 4.4 Save, Save As, unsaved changes

- Ctrl+S: incremental save in place (§3.3); Save As (Ctrl+Shift+S): full copy, then switch to it.
- The window title shows `*` while the undo position differs from the one at the last save.
- Opening another file, closing the window or quitting with unsaved changes asks "Save changes?"
  (Yes / No / Cancel) through `rfd::MessageDialog`.
- A failed save (read-only file, a removed drive) reports the error and keeps the changes; Save As
  remains possible.

### 4.5 Keyboard shortcuts (added)

| Keys | Action |
| :--- | :--- |
| Ctrl+S / Ctrl+Shift+S | Save / Save As |
| Ctrl+Z / Ctrl+Y, Ctrl+Shift+Z | Undo / redo |
| H, U, K | Highlight, underline, strike-out the selection |
| N, I, Esc | Note tool, ink tool, back to Select |
| Delete | Delete the selected annotation |

## 5. Phases

Each phase is shippable on its own and ends at a gate.

### Phase 1 - Show annotations, text markup, save

Display lists with annotations (pages, base layers and thumbnails); page revisions and tile
invalidation; the `Annotations` and `Edit` protocol; highlight, underline, strike-out, squiggly
from a selection; select, recolour and delete; Save, Save As, the title marker and the unsaved-changes
prompt; the in-place save test that CI runs on three platforms. ADR 0007 (editing model and saving).
**Acceptance:** rows P, Q, R, T, W.

### Phase 2 - Undo and redo

The journal shim (or §9 question 2's answer), the upstream PR, Ctrl+Z / Ctrl+Y, dirty state from the
undo position. ADR 0008. **Acceptance:** row S.

### Phase 3 - Notes

Placing, editing, moving and deleting sticky notes; hover preview. **Acceptance:** row U.

### Phase 4 - Ink

The ink tool, live preview, simplification, colour and width; touch draws while Ink is active.
**Acceptance:** rows V, X.

## 6. Acceptance and benchmarks

Metric definitions are in `benchmarks.md` §10.2.

| Row | Scenario | Pass |
| :--- | :--- | :--- |
| P | Existing annotations | A generated fixture with a highlight, a note, an ink stroke and a stamp renders them (pixel checks at known points) in tiles, base layer and thumbnail; 200 pages without annotations render byte-identically to today |
| Q | Markup round trip | A highlight made from a selection across two pages is saved in place; the reopened file has one highlight per page with quads equal to the selection's line boxes, and the file's original bytes are an unchanged prefix |
| R | Edit latency | `t_edit` <= 100 ms at 100% on `large_200p.pdf` (median of 20 scripted edits) |
| S | Undo / redo | 50 random edits, undo all: the annotation set equals the original; redo all: equals the final; a save after undoing writes the undone state; a mutation check (skip one journal operation) makes it fail |
| T | Unsaved changes | Open, quit and close with unsaved changes ask; Cancel keeps the document and its changes; manual check plus a unit test of the dirty state |
| U | Notes | A note's text survives save and reopen byte for byte, including non-ASCII text |
| V | Ink | A scripted 2000-point stroke: `ink_rebuild_ms` <= 4 ms per move; the committed annotation's ink list equals the simplified points |
| W | No stale pixels | `stale_tiles` = 0 over 100 scripted edits while panning; pages not edited keep their tiles (no re-render) |
| X | Memory | `ws_after_edits_n` for n = 0, 100, 1000; reported, with the journal's share |

## 7. Risks

| Risk | Impact | Mitigation |
| :--- | :--- | :--- |
| In-place save interrupted by a crash or power loss | Damaged file tail | The previous revision stays in the file (§3.3) and MuPDF repairs to it; §9 question 3's option B is atomic |
| Journal shim headers drift from the linked library | Undefined behaviour | `=0.8.0` pin and an `FZ_VERSION` equality test; the shim goes away with an upstream release |
| Saving on Linux or macOS behaves differently | Save fails there | The in-place save test runs in CI on all three platforms from Phase 1 |
| A document's existing annotations look different from other readers | Wrong rendering | It is MuPDF's renderer, the same as `mupdf-gl`; row P checks known cases |
| Many visible pages re-render after one edit | Slow edits | Only the edited page's revision changes; row W |
| The file is changed by another program while open | Save overwrites their change | Out of scope for v0.2; recorded in the backlog |

## 8. Deliberate non-goals

- **No free text, shapes or stamps** in v0.2 (the protocol's `op` grows for them later).
- **No moving or resizing** of markup and ink.
- **No annotation list panel, replies or review states.**
- **No pressure-sensitive ink** (Slint reports no pressure).
- **No editing of non-PDF documents.**

## 9. Questions for the approver

1. **Existing annotations are not drawn in v0.1** (§3.1). Fix it now as a v0.1 fix, before Phase 1
   starts, or as Phase 1's first commit?
2. **Undo mechanism** (§3.4): A - MuPDF's journal through our own `fz_try` shim in `patches/mupdf`

   mupdf-sys from a git fork.

5. **Author** (§4.3): write no author unless one is set (recommended, nothing personal goes into a

6. **Phase order:** 1 show/markup/save, 2 undo/redo, 3 notes, 4 ink - or another order?
