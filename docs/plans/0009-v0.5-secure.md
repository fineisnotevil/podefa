## 0. Gate record

Phase 0 started 2026-11-03 on the maintainer's word ("plan 0009 ile devam."), after Plan 0007
closed.

**Phase 0 gate passed, 2026-11-03.** The maintainer took every recommended answer of §9
("önerilenlerle devam") and added one requirement: make sure the text under the boxes and OCR
text are removed ("sadece redaction'da kutuların altındaki metin ve ocrların temizlendiğinden emin
ol"). The answers:

1. After a redaction the cleaned copy is written to a new file (`name-redacted.pdf` proposed) and
   opened; the original stays as it was.
2. Annotations and fields touching a mark are always removed; the document's title, author,
   subject, keywords and XMP, attachments, JavaScript and the structure tree are removed by a
   check box in Apply's dialog, on by default. Outline entries containing redacted text are listed
   for the user to decide.
3. Images blanked pixel by pixel, vector drawing removed when covered, black boxes drawn.
4. A document's permissions are followed, with the owner password to unlock them.
5. Signing certificates from a `.p12`/`.pfx` file first; PKCS#11, the Windows store and Android's
   KeyChain are decided at Phase 4.
6. `ring` with RustCrypto `cms`/`x509-cert`/`der` and a pure-Rust PKCS#12 reader.
7. Verification checks the chain to the system's roots offline and says that revocation was not
   checked.
8. Phases in the order redaction, encryption, verify, sign.

The added requirement is §3.6 and row AY.

## 1. Goal and scope

The roadmap's v0.5: **redaction, encryption, digital signatures.**

| Feature | What "done" means |
| :--- | :--- |
| Redact | Mark areas (a drag) or every match of a search; the marks show as boxes and can be moved or removed; Apply removes what is under them - text, image pixels, vector drawing, links, annotations - and draws black (or no) boxes; a file written afterwards holds none of the removed content in any form |
| Clean | Optionally remove hidden information with the redaction: document info and XMP metadata, attachments, JavaScript, the structure tree (§9 question 2) |
| Encrypt | Save with a user password (to open) and an owner password (for permissions), AES-256; change or remove the passwords |
| Permissions | A document's print, copy, edit, annotate, fill and assemble permissions are shown, and followed as §9 question 4 decides |
| Verify | A signed document shows each signature: who signed, when, whether the signed bytes are intact, whether the document changed after signing and how, whether the certificate chains to a trusted root |
| Sign | Sign an existing or new signature field with a certificate (§9 question 5), with a visible appearance; a second signature keeps the first valid |

**Out of scope, not designed out:** certifying signatures with DocMDP permissions (the signing
side), long-term validation (DSS, OCSP and CRL embedding, PAdES B-LT and B-LTA), document
timestamps, PDF/A conversion, password recovery.

## 2. What exists and what has to change

- **Opening a protected document works** (Plan 0007 Phase 5): `EngineEvent::NeedsPassword`, the
  password dialog, and the password kept in the engine (`MupdfEngine::password`) so Save As can
  reopen the copy and the tools can read the document (`tools::unlock`).
- **Save in place is incremental** (ADR 0007), which keeps existing signatures valid, and refuses
  when MuPDF says the document cannot take an incremental update (`can_be_saved_incrementally`,
  `crates/engine-mupdf/src/lib.rs:1004`): then the app asks for Save As. **Save As writes a full
  copy without garbage collection** (`lib.rs:1029`) and reopens it.
- **The annotation layer** (Plan 0004) already lists, draws, selects and deletes annotations; a
  redaction mark is one more annotation type (`Redact`), drawn by MuPDF as an outlined box.
- **Signature fields** are read as widgets of type `Signature` (Plan 0006) and left alone.
- **Tools write from a separate document** (Plan 0005 §3.4): the open document's current state is
  written to memory and read again.

## 3. Phase 0 findings (verified, with evidence)

### 3.1 Redaction: MuPDF has it, mupdf-rs 0.8 wraps it

- `pdf_redact_page` and `pdf_apply_redaction` (`pdf/page.h:300`, `pdf/annot.h:1026`) are wrapped
  as `PdfPage::redact_with_options` and `PdfAnnotation::apply_redaction_with_options`
  (`patches/mupdf/src/pdf/page.rs:511-523`, `annotation.rs:367-383`), with every option
  (`PdfRedactOptions`: black boxes; images untouched, removed or blanked pixel by pixel; vector
  drawing removed if covered or if touched; text removed, kept, or only invisible text removed).
- Applying is one journal operation of MuPDF's own (`pdf-clean.c:1145-1167`) and costs 0.3 ms on
  the generated page (§15.1). Undo brings the content back and redo removes it again, as long as
  no garbage-collecting save of the open document came between (§15.1).
- What MuPDF removes (`pdf-clean.c:1122-1176`): the page content under the marks (text, images,
  vector drawing by the options), links touching the marks, free-text annotations touching them,
  and the redaction annotations. Patterns, soft masks and Type 3 fonts are not filtered
  (`filter_opts.recurse = 0`, `pdf-clean.c:1089`).
- **What it leaves:** every other annotation over the area and form fields with their values
  (only free text is deleted, `pdf-clean.c:1036-1054`), the document title and XMP metadata,
  outline entries, attachments, the structure tree. Measured for a highlight over the line with
  its comment, the title and the outline (§15.1); the rest is read from the source. The app must remove
  annotations and fields that touch a mark itself, and offer the clean-up of §1.

### 3.2 Found: a redacted document saved as the app saves it today keeps the secret

- MuPDF marks a redacted document as not saveable incrementally (`doc->redacted`,
  `pdf-write.c:1988-1995`) but **does not refuse an incremental save**: one wrote a file with all
  7 copies of the secret, the original bytes intact before the appended redaction (§15.1). The
  app's in-place Save checks first and asks for Save As.
- **Save As, a full save without garbage collection, also kept all 7 copies**: the replaced
  content stream is written although nothing refers to it any more. Only a save with garbage
  collection dropped it (5 copies left, all in the parts of §3.1 MuPDF does not touch).
- A garbage-collecting save of the open document breaks its undo (Plan 0005 §3.4; seen again
  here: the undone page had no text). So the write of a redacted document is like a tool's: write
  the current state to memory, read it as a second document, save that with garbage collection
  (and the §3.1 clean-up), then open the result.
- The same holds for every other way the document leaves the app: the tools write from the
  in-memory state (Extract and Split graft only reachable objects; Compress collects garbage; a
  plain full write does not), and the search thread reads a snapshot of it
  (`search.document_bytes`, `lib.rs:1611`). Phase 1 checks each one with the secret search of
  §15.1.

### 3.3 Encryption: written by MuPDF, wrapped by mupdf-rs, with two flaws

- `PdfWriteOptions` sets the method (RC4 40 and 128, AES 128 and 256), the user and owner
  passwords and the permissions (`patches/mupdf/src/pdf/document.rs:179-226`). Its default keeps a
  document's encryption as it is (`do_encrypt` 0 is `PDF_ENCRYPT_KEEP`, `pdf/crypt.h:31`), so the
  app's saves already keep it: an annotation saved in place in an AES-256 document stayed
  encrypted (§15.1).
- Changing the encryption needs a full save: MuPDF throws "Can't do incremental writes when
  changing encryption" (`pdf-write.c:2729-2730`). A full save invalidates signatures (§3.5).
- AES-256 took 12 ms to save a 24 KB file and 53 ms to reopen it and try a wrong and the right
  password, against 1 ms and 9 ms for AES-128: its key derivation (§15.1). Turkish passwords work: MuPDF takes them as UTF-8 and prepares them itself.
- **Flaw 1:** `PdfDocument::permissions` always reports every permission for an encrypted
  document: it reads MuPDF's `/P` with `Permission::from_bits`, which fails on the reserved bits a
  real `/P` has set, and falls back to `Permission::all()` (`document.rs:841-844`; §15.1).
  `from_bits_truncate` fixes it; a patch in `patches/mupdf` and an upstream pull request.
- **Flaw 2:** `set_user_password` and `set_owner_password` `assert!` that the password is shorter
  than 128 bytes (`document.rs:203`, `:221`), and the `permissions()` getter of the write options
  unwraps MuPDF's default `~0` (`:189`). The app checks the length before (a typed error) and
  never calls the getter.
- **Owner passwords are advice.** A document opened with the user password was saved without
  encryption and then opened with no password (§15.1); MuPDF reports the permissions and leaves
  it to the application to follow them (`pdf_has_permission`, `pdf-crypt.c:836-855`). §9
  question 4.

### 3.4 Signatures: MuPDF does the PDF part, the cryptography is ours

- MuPDF writes and checks the signature's PDF structure: `pdf_sign_signature` and
  `pdf_sign_signature_with_appearance` (`pdf/form.h:279-305`) fill a field's value (`/ByteRange`,
  room for `/Contents`, `/M`, a FieldMDP reference; `pdf-form.c:1906-1990`), and the save fills
  in the byte range and the digest (`complete_signatures`, `pdf-write.c:1608-1720`).
  `pdf_check_digest`, `pdf_check_certificate`, `pdf_signature_incremental_change_since_signing`
  and `pdf_validate_change_history` (`pdf/form.h:268-271`, `pdf/crypt.h:95`, `pdf/xref.h:265`)
  check them.
- **The cryptography comes from a signer and a verifier**, structs of callbacks
  (`pdf_pkcs7_signer`: the signer's name, the maximum size of the signature, and
  `create_digest`, which gets the signed bytes as a stream and returns the whole CMS blob;
  `pdf_pkcs7_verifier`: `check_certificate`, `check_digest`, `get_signatory`;
  `pdf/form.h:214-251`). MuPDF's own are built on OpenSSL (`helpers/pkcs7/pkcs7-openssl.c`); the
  mupdf-sys build has no OpenSSL, so they throw "No OpenSSL support" (`pkcs7-openssl.c:28-40`).
- **mupdf-rs 0.8 wraps none of it** beyond creating an empty signature field
  (`PdfPage::add_signature_widget`, `page.rs:495`). mupdf-sys binds the functions and the structs
  (`bindings.rs`), unguarded: like Plan 0005's, each needs an `fz_try` wrapper in
  `patches/mupdf/journal/`, and the callbacks need C trampolines that turn a Rust error into
  `fz_throw` (a Rust callback must not unwind through C).
- **The format MuPDF writes is `adbe.pkcs7.detached`** (`pdf-form.c:1944-1945`). PAdES baseline
  (B-B, what EU and Turkish readers expect of a new signature) needs `ETSI.CAdES.detached` and a
  signing-certificate-v2 attribute in the CMS; the attribute is ours (we build the CMS), the
  `/SubFilter` is one more line in the wrapper after `pdf_signature_set_value`.
- **The crypto library** (§9 question 6), not yet measured:
  - RustCrypto `cms` (CMS structures with a `SignedDataBuilder`), `x509-cert`, `der`, `pkcs8`,
    and a PKCS#12 reader (`p12-keystore` reads modern PBES2 and legacy 3DES files; RC2-40 support
    is unclear). Pure Rust, builds for Android as-is.
  - **The `rsa` crate has an open advisory** (RUSTSEC-2023-0071, the Marvin timing attack) with no
    patched release; only 0.10 release candidates carry the constant-time rewrite. `cargo deny`
    would fail on it; an ignore needs a recorded reason (signing on the user's machine is not a
    network oracle) or another RSA implementation.
  - `ring` (RSA PKCS#1 v1.5 and ECDSA P-256/P-384 signing and verification, maintained, some C and
    assembly) for the arithmetic, with RustCrypto only for the structures, avoids that crate.
  - OpenSSL through MuPDF's own signer: least code, but a system library on Linux and macOS and a
    vendored build on Windows and Android, against the resource priority.
- **Certificates.** A `.p12`/`.pfx` file with a password is the portable source. Turkish
  qualified e-signatures (e-İmza) live on smart cards and USB tokens behind PKCS#11; Windows
  keeps certificates in its store (CNG), Android in its KeyChain. Each is its own work (§9
  question 5).
- **Trust.** "The bytes are intact" needs only the CMS; "the signer is who they say" needs a chain
  to a trusted root - the system's roots on Windows, macOS and Android, a CA bundle on Linux - and
  revocation, which needs the network (§9 question 7).

### 3.5 Signatures and the rest of the app

- **Save in place keeps signatures valid** (incremental, ADR 0007). Everything that rewrites the
  file breaks them: Save As (a full copy), changing the encryption (§3.3), applying a redaction
  (§3.2), every tool of Plan 0005 that writes a new file, and a Save after a page edit when the
  document repaired at open. The app must say so before it does it.
- **Changes after signing are judged by the signature's permissions.** A DocMDP level 1 forbids
  any change, level 2 allows filling forms and signing, level 3 also annotations
  (`pdf_validate_change_history`, `pdf_find_locked_fields`, `pdf/xref.h:250-265`). An annotation
  added to a level-1 or level-2 document makes the signature "changed after signing" in every
  reader; the app should warn before the first edit of a certified document.
- **Redaction and signatures:** a redacted document cannot keep a signature over the removed
  content; Apply warns when the document is signed.
- **Backlog item 30** (Markdown notes stored in the PDF) needs the redaction to clean the notes too.

### 3.6 Text and OCR under a mark (Phase 1, measured)

Measured for the gate's added requirement ([`../benchmarks.md`](../benchmarks.md) §15.2): one page
with a different secret in each of 13 places a page keeps text under a box.

- **MuPDF removes:** visible text; an OCR layer's invisible text (render mode 3, also scaled with
  `Tz`); clipping text; zero-alpha text; text in a form XObject (it filters an instanced copy);
  text in a hidden optional-content layer; a structure element's `/ActualText` for a marked
  sequence under the box (it edits the element). It blanks a scanned image's pixels under the box.
  A glyph is removed when its box, shrunk by a tenth on each side, meets a mark
  (`pdf_redact_text_filter`, `pdf-clean.c:536-591`).
- **MuPDF leaves, so the app removes** (§4.1):
  - an inline `/ActualText`, `/Alt` or `/E` of a marked sequence whose glyphs it removed;
  - text inside tiling patterns and soft masks (`recurse = 0`, `pdf-clean.c:1089`): still drawn
    and extracted under the box while the fill that uses them stays, and in the file even when the
    fill is removed, because the page's resources keep naming them;
  - the page's `/Thumb` (a picture of the unredacted page) and `/PieceInfo` (an editor's private
    data, which can hold a copy of the content).
- **Found on the way:** Compress keeps its input when the output is not smaller
  (`tools.rs`, `kept_original`); for the open document that input is the snapshot written without
  garbage collection, so after a redaction it would hold the removed content. A redacted document
  never keeps its input.
- **Not covered:** text that is only pixels of a scanned image is redacted as pixels (§8: no OCR
  before redaction).

## 4. Design

### 4.1 Engine

- **Redaction marks** are `Redact` annotations, added, moved and deleted as other annotations
  (`EditOp::AddRedaction { page, rects }`, one journal step). Search-and-redact adds one mark per
  match on every page in one step.
- **Apply** (`EditOp::ApplyRedactions { pages, options }`) is one journal step: before MuPDF's
  `redact_with_options`, the engine deletes every annotation and form field that touches a mark
  (MuPDF leaves them, §3.1). It sets a document flag, `redacted`, that Save reads.
- **After MuPDF's pass** (§3.6), on each redacted page:
  1. text that MuPDF's stext device still finds with its centre under a mark can only come from a
     pattern, a soft mask or a Type 3 glyph; if there is any, the marks are applied again with
     drawing removed when it *touches* a mark, and if text is still there, Apply fails and the
     document is left as it was;
  2. an inline `/ActualText`, `/Alt` or `/E` (or a named `/Properties` entry with them) is removed
     from every marked sequence whose content MuPDF changed, found by comparing each sequence's
     text, images and forms with the page's content before Apply (`pdf_core::content`, a content
     stream tokenizer);
  3. the page's resources are cut to what its content still names, so a pattern, soft mask, font
     or image no longer drawn there is not written;
  4. `/Thumb` and `/PieceInfo` are removed.
- **Writing a redacted document** goes through the tool path (§3.2): the current state written to
  memory, read as a second `PdfDocument`, cleaned (§1, by the options of §9 question 2), saved with
  garbage collection, compression and the encryption the user chose, then opened as the document.
  Save in place does the same into a temporary file next to the original, closes the actor's and
  the search thread's documents, replaces the original and reopens (§9 question 1).
- **Encryption** is an option of Save As (`EngineCmd::Save { path, encryption }`) through
  `PdfWriteOptions`; `pdf_core::secure::{Encryption, Permissions}` in core.
- **Permissions** come from a `fz_try` shim of `pdf_has_permission` per permission, or from the
  patched `permissions()` (§3.3), and travel with `Opened`.
- **Signatures**: `pdf_core::signature::SignatureInfo { field, page, rect, signer, time, reason,
  location, digest: Intact | Broken | Unknown, certificate: Trusted | Untrusted(why) | Unknown,
  changed_after: None | Allowed | Disallowed }`, sent with `Opened` and after each save. The
  verifier and signer are Rust code behind C trampolines in `patches/mupdf/journal/`.

### 4.2 App

- **Edit mode gets a Redact tool** (its own tint, like the markup tools): a drag marks an area; a
  click on a mark selects it. Its palette has Apply, Search and mark, and Clean-up options. Apply
  asks once (it cannot be undone after the save, and the save writes a new file).
- **Save As** gets a Protect section: a password to open, an owner password, the permissions;
  File > Protect for the same on the open document.
- **The status bar** shows a lock for an encrypted document (its permissions in a popup) and a
  signature mark for a signed one; the signature panel (sidebar) lists the signatures with their
  state; a signature field on the page shows its state on hover.
- **Signing**: a click on an empty signature field (or Sign in the Tools island) opens the sign
  dialog: certificate, reason, location, an appearance preview (`pdf_preview_signature_as_*`).

## 7. Risks

| Risk | Impact | Mitigation |
| :--- | :--- | :--- |
| A copy of redacted content left somewhere | The feature's whole point fails | Row AY searches every exit; the redacted save always collects garbage |
| Content MuPDF does not filter (patterns, soft masks, Type 3 fonts, §3.1) | Text drawn through them survives | Tested in Phase 1; if found, rasterize the marked area of such a page (§9 question 3) |
| `rsa` advisory, crypto size | `cargo deny` fails, a bigger binary | §9 question 6; measured in Phase 4 |
| Readers that disagree on a signature's state | A signature valid here is shown invalid elsewhere | Row BD in another reader; PAdES B-B |
| Smart-card e-signatures | Turkish qualified signatures need PKCS#11 | §9 question 5 |

## 8. Deliberate non-goals

- No certifying (DocMDP) signatures, no long-term validation, no document timestamps (§1).
- No password recovery and no removal of a password the user does not have.
- No OCR before redaction: scanned text is redacted as image pixels.

## 9. Questions for the approver

1. **Saving after a redaction** (§3.2, §4.1):
   - **A (recommended):** Apply asks for a new file name (`name-redacted.pdf` proposed), writes the
     cleaned copy and opens it; the original file stays as it was. As Acrobat does.
   - **B:** Save replaces the original with the cleaned file (temporary file, close, replace,
     reopen; the undo history starts again).
2. **Clean-up with a redaction** (§1, §3.1): annotations and fields touching a mark are always
   removed. Besides that, remove the document's title, author, subject, keywords and XMP,
   attachments, JavaScript and the structure tree:
   - **A (recommended):** a check box in Apply's dialog, on by default;
   - **B:** always;
   - **C:** never (a separate "Remove hidden information" tool later).
   And the outline: keep it, but list entries containing marked text so the user decides
   (recommended), or leave it alone.
3. **Images and drawing under a mark:** images blanked pixel by pixel (MuPDF's default,
   recommended) or removed whole; vector drawing removed when covered (recommended) or when
   touched; black boxes drawn over the areas (recommended) or not.
4. **Permissions of an opened document** (§3.3), opened with the user password:
   - **A (recommended):** followed - printing, copying, editing, annotating, filling and page
     tools are off where the document says so, with the owner password as a way to unlock them;
   - **B:** shown but not followed (as many open-source readers do);
   - **C:** followed, with a setting to ignore them.
5. **Certificate sources for signing** (§3.4): a `.p12`/`.pfx` file (Phase 4, recommended as the
   first); also PKCS#11 smart cards and tokens (e-İmza), the Windows certificate store, Android's
   KeyChain - in Phase 4, in a later phase, or not at all?
6. **The crypto library** (§3.4):
   - **A (recommended):** `ring` for RSA and ECDSA, RustCrypto `cms`/`x509-cert`/`der` for the
     structures, a pure-Rust PKCS#12 reader; Phase 4 measures the binary size.
   - **B:** RustCrypto throughout, `rsa` included, with a `deny.toml` ignore for RUSTSEC-2023-0071
     and its reason.
   - **C:** OpenSSL through MuPDF's own signer and verifier.
7. **Trust when verifying** (§3.4): check the chain to the system's roots without the network
   (recommended; the state says "revocation not checked"), also check revocation online (OCSP and
   CRL, the app's first network access), or only report that the bytes are intact.
8. **Phase order:** redaction, encryption, verify, sign (recommended), or signatures first?
